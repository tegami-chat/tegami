よくある構成とTegamiの違いを、場面ごとに確かめたい開発者のために、7つの場面で並べて比べます。表の左がよくある構成、右がTegamiです。技術用語は、初めて出てきたところで一文で説明します。ほかの用語は、[技術仕様の用語](/ja/developers/spec/#用語)にあります。

## 計測と広告

Tegamiのウェブ版は、トラッカーも広告SDKも入れていません。CSP（Content Security Policy。ページが読み込める送信元をブラウザに制限させる仕組み）で、読み込めるスクリプトを自身のオリジンと、新規登録時の人間確認に使うCloudflare Turnstileだけに限っています。広告や解析のスクリプトはありません。

| よくある構成 | Tegami |
| --- | --- |
| リモート設定でトーク一覧に広告枠が差し込まれる | トーク一覧には、端末に保存した会話だけを表示する |
| タブにニュースやコマースへの導線が並ぶ | 切り替えは「トーク」と「友だち」の2つだけ。広告や余分な画面をリモート設定で差し込む仕組みはない |
| 誤タップもクリックとして計測される | タップや画面表示を、計測イベントとして送信しない |

CSPは`script-src 'self' https://challenges.cloudflare.com`です。`connect-src`は、自身のオリジンとリレーだけです。Cloudflare Web Analytics（RUM）は無効です。そのほか外部へ出る通信は、リレー経由のファイルストレージ（R2）、通話用のSTUN（`stun.cloudflare.com`）、Web Pushサービスです。R2はCloudflareのオブジェクトストレージ、STUNは通話で端末の外から見える経路を調べる仕組み、Web Pushはブラウザやアプリが閉じていても通知を届ける仕組みです。

## アカウントと鍵

Tegamiのアカウントは、電話番号ではなく、端末で作るNostrの鍵ペア（secp256k1）です。秘密鍵は、WebAuthn（パスワードなしでブラウザやOSの認証を使うWeb標準）の[PRF](/ja/developers/spec/#用語)拡張の出力から作ったAES-GCM（暗号化と改ざんの検知を同時にできる暗号方式）の鍵で暗号化し、端末内に保存します。

| よくある構成 | Tegami |
| --- | --- |
| SMSの認証コードで電話番号を確かめる | 端末で鍵ペアを生成する |
| 番号がサーバーのユーザーテーブルに登録される | 秘密鍵は、PRFの出力から作ったAES-GCMの鍵で暗号化し、端末内に保存する |
| その番号がアカウントに紐づけられる | [NIP-98](/ja/developers/spec/#用語)で署名したリクエストで、公開鍵をリレーに登録する |

登録には、招待券かCloudflare Turnstileを使います。Turnstileは、ブラウザの環境を調べてボットを見分けるCloudflareの人間確認です。誰が誰を招待したかの記録は、90日で消します。

署名にはSchnorr署名（secp256k1上の電子署名）を使います。鍵の導出にはHKDF（秘密の値から、暗号に使う固定長の鍵を作る方法）、暗号化にはAES-GCMを使います。PRF拡張に非対応の認証器では、取り出せない設定のAES鍵をIndexedDBに保存します。

## 暗号化

よくあるアプリのサーバーは、送信者、受信者、時刻をデータベースに記録します。Tegamiは、[rumor](/ja/developers/spec/#用語)（[kind](/ja/developers/spec/#用語) 14または15）をNIP-44で暗号化して、送信者が署名した内側の層（seal、kind 13）に収めます。さらに、使い捨ての鍵で再びNIP-44による暗号化と署名をして、[封筒](/ja/developers/architecture/#封筒)で包みます。1対1では、宛先用と自分用の控えの2通を送ります。

| よくある構成 | Tegami |
| --- | --- |
| メッセージはTLS（アプリによってはE2EE）でAPIサーバーに届く | 端末内でメッセージをNIP-44で暗号化し、内側の層と封筒で二重に包む |
| サーバーが送信者、受信者、時刻をデータベースに残す | リレーは、[NIP-42](/ja/developers/spec/#用語)で認証済みの鍵に対し、`p`タグが一致するkind 1059だけを返す |
| そのイベントログが広告配信に使われる | リレーは30日後に封筒を削除し、履歴は利用者の端末に残る |

内側の層と封筒の`created_at`は、最大2日前にずらします（nostr-toolsのNIP-59の実装）。TLSは通信経路を暗号化する標準のしくみ、E2EEは送る端末で暗号化して受け取る端末だけが復号する方式です。

<Aside type="caution" title="限界">

書き込みにもNIP-42の認証と事前の登録が必要なため、リレーは、送信元の公開鍵、宛先の公開鍵、到着時刻、IPアドレスを結びつけられます。NIP-44は同じ鍵を使い続けるため、前方秘匿性はありません。

</Aside>

## 保存

Tegamiのリレーは、データベースが丸ごと持ち出されても、トークの中身は暗号文のままです。リレーのデータベースに保存されるメッセージは、封筒の暗号文です。写真やファイルも、個別の鍵を使ってAES-GCMで暗号化してから、ストレージにアップロードします。

| よくある構成 | Tegami |
| --- | --- |
| データベースに個人情報がまとまって入っている | データベースのメッセージは、kind 1059の暗号文 |
| データベースが外に持ち出される | 同じく、データベースが外に持ち出される |
| 電話番号やプロフィールが平文のまま読まれる | 持ち出されても、受信者の秘密鍵がなければ復号できない |

持ち出される可能性があるものは、次のとおりです。宛先の公開鍵（`p`タグ）、到着時刻、登録済みの公開鍵と招待関係（90日保持）、Web Pushのエンドポイント（ブラウザのプッシュサービスが発行する、通知の宛先のURL）と鍵、暗号化した復旧用バックアップ、R2の暗号化ファイルとスタンプ（サイズ、SHA-256、保持者情報を含む）、通報記録です。通報記録には、通報者と相手の公開鍵、理由が入り、添付された場合は直近メッセージの平文を90日保持します。

持ち出されても読めないものは、通常のメッセージ、写真、ファイル、スタンプ、バックアップの平文です。

## ログイン

Tegamiには、ログインのパスワードがそもそもありません。中継型フィッシングは、本物のログインサイトと利用者の間に偽サイトを挟み、入力を中継する攻撃です。秘密鍵（nsec）は端末で生成し、WebAuthnのPRF拡張の出力から作った鍵で暗号化して、オリジンごとの保存領域に置きます。パスキー（生体認証や端末のロック解除で使う、オリジンに紐づく資格情報）はオリジンに紐づくため、偽のドメインではPRFの出力が得られず、復号できません。

| よくある構成 | Tegami |
| --- | --- |
| パスワードとSMSのワンタイムコードでログインする | 端末に保存したnsecをパスキーで復号する |
| 中継型フィッシングで両方を横取りされる | 偽のドメインではPRFの出力が得られず、復号できない |
| 攻撃者がセッションを手に入れる | nsecはサーバーに送信しない |

<Aside type="caution" title="限界">

復号した秘密鍵は、ブラウザのメモリ上で署名に使うため、XSS（Webページに悪意のあるJavaScriptを実行させる攻撃）や、配信するJavaScriptの改ざんには弱いです。PRF拡張に非対応の認証器では、取り出せない設定のAES鍵をIndexedDBに保存します。復旧コードは、偽サイトに入力させる手口で盗まれるおそれがあります。

</Aside>

## 利用の記録

Tegamiのアプリには、解析SDKがありません。リレーは、日ごとの全体件数を183日保持して運営者向けに集計し、終わった週の合計だけを直近24週分、外部に公開しています。公開先は`https://relay.tegami.chat/stats`と`https://tegami.chat/status`です。

| よくある構成 | Tegami |
| --- | --- |
| 解析SDKが、タップや画面表示をイベントとして送る | クライアントは、操作イベントを送らない |
| イベントがユーザーIDごとに保存される | リレーは、日ごとの全体件数だけを内部で数え、アクティブ鍵数の概算には、日替わりの秘密の値と[HyperLogLog](/ja/developers/spec/#用語)を使う |
| その記録から、興味のセグメントが作られる | 公開するのは、終わった週の合計（0から9は0、10以上は10の倍数に切り上げ）と、1日平均の鍵数だけ |

Workersのinvocation logs（リクエストごとの実行の記録）は無効です。ユーザーが許可したクラッシュ報告などの出力（`console.log`）は、Workers Logsに最大7日間残ります。日ごとの集計は183日で削除し、運営者だけが閲覧できます。公開ページには、終わった週（UTCの月曜始まり）を、直近24週分だけ出します。

## AI

Tegamiでは、AIは自分の鍵を持つ相手です。`tegami-agent`は、パソコン上で独自のNostr鍵を持ち、人間と同じNIP-17でやり取りします。AIの契約やAPIキーを、Tegamiのサーバーに渡すことはありません。AIに読ませた内容は、手元の`claude -p`（Claude Codeを、プロンプトを直接渡して結果を標準出力に返す形で動かすコマンド）などを通じて、AIの提供元に送られます。`tegami-agent`は、MCPサーバー（AIが外部のデータや機能を共通の形式で呼び出すための仕組み）としても動きます。

| よくある構成 | Tegami |
| --- | --- |
| アプリに組み込まれたAI機能を使う | `tegami-agent`がパソコン上で動き、手元のClaude Codeなどを呼ぶ |
| 相手の発言を含むトーク履歴が、提供元のAPIに送られる | トークにAIを呼ぶ前に、全員の同意を求める（公開待ち） |
| 相手の同意は求められない | AIの権限を、全体、モデル、AI、友だちの4段で制御し、判断はすべて端末に記録する |

AIとの会話も、NIP-17の封筒です。トークにAIを呼ぶ前に全員の同意を求める仕組みは、実装済みですが、本番にはまだ出していません。相手が「自分の文を相手のAIに読ませない」を選べる仕組みは、本番で動いています。受信者が自分の端末で復号した発言をAIに渡す行為までは、暗号の仕組みでは防げません。
