This page explains how messages are encrypted, what the server can see, and where the weak points are, for people who want to check.

## What the server can see

The Tegami relay cannot read message contents. All the relay can see is:

- The recipient's public key on each [envelope](/developers/architecture/#envelopes) (the envelope's `p` tag), the time it arrived, and its size
- The keys logged in and connected, and the IP address they connect from
- Tags on the outside of the envelope: whether it is a call (`t=call`), whether it should not trigger a notification (`t=quiet`), and its expiry (`expiration`)
- Beyond envelopes: who invited whom at registration (deleted after 90 days), the keys that stored stickers and their sizes, and the contents of reports (deleted after 90 days)

An envelope hides the sender by itself, but because the Tegami relay requires login for writes too, at the moment it accepts an envelope it knows which key sent it to which key. However, the relay code does not store the sender's key (in `relay/src/index.ts`, the `events` table has no sender column). The one exception: envelopes sent by people who registered without an invite code are stored with a marker, so the app shows them only when the sender is already a friend.

<Aside type="caution" title="What outsiders cannot verify">

There is no way for anyone outside to verify that the running relay is the same as the published code. The relay reports its running commit in `/stats` and in the NIP-11 `version`, but that is only our own claim. <Badge text="Under discussion" variant="caution" /> We have not yet decided how to let outsiders verify it.

</Aside>

## Forward secrecy

Tegami has no forward secrecy. NIP-44 derives its encryption key from the long-term keys of the sender and the recipient. If a secret key is stolen, envelopes still on the relay (up to 30 days) and messages stored on devices can be decrypted later. Only the outer layer of an envelope uses a fresh throwaway key each time.

Tegami makes up for this by encrypting your secret key with a passkey, which makes the key itself harder to steal. Where the passkey does not support [PRF](/developers/spec/#glossary), it uses a non-extractable key on the device instead. Compared with schemes like Signal or MLS that keep rotating keys, this is a weakness.

- <Badge text="Under discussion" variant="caution" /> We have not decided whether to move to a scheme that keeps rotating keys.

## Group encryption

Tegami groups follow the NIP-17 spec and build a separate envelope for each member. For example, one message to a group of you plus 5 others becomes 6 envelopes, including your own copy. The relay cannot tell who is in the same group.

The number of envelopes grows with group size, so this does not suit large groups. We do not use MLS.

## The browser version and malicious JavaScript

The browser version has a weakness shared by every encrypted app that runs in a browser. If the source that serves it (`app.tegami.chat` on Cloudflare) is tampered with, it could serve code that steals keys. That is why Tegami sets a strict CSP that limits where code can load from, and includes no third-party analytics scripts at all.

There is no way yet to verify that the files we serve were built from the public repository (reproducible builds plus verification). Versions distributed through app stores are fixed, so shipping apps will make this weakness smaller.
