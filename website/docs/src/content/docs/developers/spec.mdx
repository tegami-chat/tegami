Crypto building blocks, relay limits, HTTP endpoints and Tegami's own event kinds.

Status labels such as "Available" are explained in the [overview](/developers/#what-the-status-labels-mean).

## Cryptography

| Where | Scheme |
| --- | --- |
| Messages | NIP-44 v2 (secp256k1 ECDH, HKDF, ChaCha20, HMAC-SHA256). Double-wrapped with a seal and gift wrap per NIP-59 |
| Secret key storage | Takes 32 bytes from the passkey PRF extension (`userVerification: required`) and turns it into an AES-GCM 256-bit key with HKDF-SHA256 for encryption. Without PRF, a non-extractable AES-GCM key is kept in IndexedDB |
| Photos and files | A new AES-GCM 256-bit key per file. The key and the sha256 of the encrypted data are sent inside the encrypted message (kind 15). Sticker keys are derived from the image and the account's secret key |
| Recovery code | 28 characters (140 bits) fed through HKDF-SHA256 to create three things: a backup ID, an AES-GCM key, and a Nostr signing key |
| Device transfer | Envelope encrypted with NIP-44 to a throwaway key, with a 10-minute NIP-40 expiry. The throwaway secret key is included only after the `#` in the link |
| Notifications | Web Push (VAPID). Payload encrypted per device with RFC 8291 (aes128gcm) |
| Calls | WebRTC (DTLS-SRTP). Signaling in NIP-17 envelopes (custom kind 25050, 1-minute expiry) |

## NIPs in use

<Aside type="tip" title="Now">

| NIP | Usage |
| --- | --- |
| NIP-17, NIP-59 | One-to-one and group messages. Text uses kind 14, photos and files use kind 15, wrapped in a seal (kind 13) and gift wrap (kind 1059) |
| NIP-44 | Encryption of seals and gift wraps, and of device transfer data |
| NIP-42 | Authentication (login) to the relay. Both reads and writes require an authenticated key |
| NIP-40 | Expiring envelopes (1 minute for call signals, 10 minutes for device transfer and AI draft requests) |
| NIP-98 | Signatures for HTTP endpoints (registration, notifications, recovery backups, reports, admin operations) |
| NIP-05, NIP-11 | Identifier for the official account (hello@tegami.chat), plus relay info and the running version |
| Blossom (kind 24242 signatures) | Storage for photos and files (`/upload` and `/<sha256>`). Data is stored and fetched by the sha256 of the encrypted bytes. `/stamp` for stickers is a Tegami-specific extension |

Where no NIP covers what we need, we use our own kinds, only inside encrypted envelopes: icon (10100), sticker list (10101), call signaling (25050), and AI draft requests and replies (25060, 25061).

</Aside>

## What the relay accepts

-   Over WebSocket, the only events accepted are kind 1059 (gift wrap) with exactly one recipient (`p` tag). Size limit 128KB
-   Reads and writes are allowed only for keys logged in with NIP-42. Login signatures are valid for 10 minutes, and each connection can hold up to 20 subscriptions
-   Only registered, non-suspended keys can write. You can read only envelopes addressed to you, up to 500 per fetch, deleted after 30 days. Each inbox holds up to 10,000 envelopes, and up to 200 from people registered without an invite code
-   Sending limits (token bucket): per IP address, a burst of 300 (then 5 per second); per key, a burst of 120 (then 3 per second). Up to 50 connections per IP address

HTTP endpoints (photo, file, and sticker operations require a kind 24242 signature; other writes require a NIP-98 signature; only `/crash` needs no signature):

| Endpoint | Purpose | Status |
| --- | --- | --- |
| `POST /register` | Register a key (invite code or Turnstile) | <Badge text="Available" variant="success" /> |
| `PUT /upload`, `GET` and `HEAD /<sha256>` | Store and fetch photos and files. Up to 10MB | <Badge text="Available" variant="success" /> |
| `PUT /stamp`, `GET`, `HEAD` and `DELETE /stamp/<sha256>` | Stickers. 512KB each, up to 200 per person | <Badge text="Available" variant="success" /> |
| `PUT`, `GET`, `DELETE /backup/<id>` | Recovery code backup. Up to 64KB | <Badge text="Available" variant="success" /> |
| `POST`, `DELETE /push`, `GET /push/key` | Register notification endpoints, and the notification public key | <Badge text="Available" variant="success" /> |
| `POST /report` | Reports | <Badge text="Available" variant="success" /> |
| `GET /stats` | Weekly usage statistics (public) | <Badge text="Available" variant="success" /> |
| `POST /crash` | Error reports, only when the user allows (not stored) | <Badge text="Available" variant="success" /> |
| `POST /admin` | Admin operations such as suspending keys, usable only with the operator's key | <Badge text="Available" variant="success" /> |
| `POST /register` (AI) | Register an AI key. The body carries the owner card (kind 25070); the relay remembers the key as an AI and counts its daily limits | <Badge text="Available" variant="success" /> |
| `POST /turn` | Short-lived TURN credentials for calls, for registered keys only. Nothing about the request is kept | <Badge text="Available" variant="success" /> |
| `DELETE /account` | Delete the account. The relay removes the envelopes, stamps, notification endpoints and registration it holds for the key | <Badge text="Available" variant="success" /> |
