This page collects the spec so that people checking Tegami's implementation, or building their own, can look up the encryption, the NIPs, the relay limits, the HTTP endpoints, and the custom kinds.

## Glossary

| Term | Meaning |
| --- | --- |
| kind | An integer that says what type a Nostr event is. 1059 is an envelope, 14 is a text message, and 15 is a photo or file |
| rumor | The event that holds the message itself, with no signature (kind 14 or 15) |
| seal | The inner event that encrypts the rumor with NIP-44 and is signed by the sender (kind 13) |
| Envelope (gift wrap) | The outer event that encrypts the seal with NIP-44 using a throwaway key and is signed with that key (kind 1059). It is defined in NIP-59 |
| Durable Object | A unit of execution on Cloudflare Workers that can keep data. Tegami's relay stores envelopes in SQLite inside a single Durable Object |
| HyperLogLog | A method that gives only the approximate count of distinct items, using little memory and without remembering the items |
| Salt | A value mixed into the input of a cryptographic function. Tegami changes it every day and discards it when the day changes, so the same key cannot be followed across days |
| Blossom | A file-storage spec for Nostr that stores and fetches photos and files by their sha256. It uses kind 24242 for signatures |
| NIP-98 | A spec that signs an HTTP request's URL and method with the secret key and uses it for authentication |
| Token bucket | A limit that counts how much you can send by the number of tokens saved up. Sending uses tokens, and they refill at a steady rate. The "burst" below is the most tokens that can be saved up |
| PRF | A WebAuthn extension (Pseudo-Random Function). Each time you authenticate with a passkey, it returns a value fixed for that passkey |
| NIP-42 | A spec where the connecting side signs a challenge the relay issues, to show its public key |

## Cryptography

| Where it is used | Method |
| --- | --- |
| Messages | NIP-44 v2 (secp256k1 ECDH, HKDF, ChaCha20, HMAC-SHA256). Wrapped twice in the NIP-59 way, with the outer layer as the envelope |
| Storing the secret key | Takes 32 bytes from the passkey [PRF](#glossary) extension (`userVerification: required`), turns it into an AES-GCM 256-bit key with HKDF-SHA256, and encrypts with it. Where PRF is unavailable, a non-extractable AES-GCM key is kept in IndexedDB |
| Photos and files | A new AES-GCM 256-bit key per file. The key and the sha256 of the encrypted data travel inside the encrypted message (kind 15). Stickers derive the key from the image and the account's secret key |
| Recovery code | From 28 characters (140 bits), HKDF-SHA256 makes three things: a backup ID, an AES-GCM key, and a Nostr key for signing |
| Device transfer | An envelope encrypted with NIP-44 to a throwaway key, with a 10-minute expiry set by NIP-40. The throwaway secret key is included only after the `#` in the link |
| Notifications | Web Push (VAPID). The content is encrypted for each device with RFC 8291 (aes128gcm) |
| Calls | WebRTC (DTLS-SRTP). Signaling goes in NIP-17 envelopes (custom kind 25050, 1-minute expiry) |

## NIPs in use

| NIP | How it is used |
| --- | --- |
| NIP-17, NIP-59 | One-to-one and group messages. Text uses kind 14 and photos and files use kind 15, wrapped twice: a signed inner layer (kind 13) and an envelope (kind 1059) |
| NIP-44 | Encrypting the inner layer and the envelope, and encrypting the device transfer data |
| NIP-42 | Authentication (login) to the relay. Both reading and writing are allowed only for authenticated keys |
| NIP-40 | Envelopes with an expiry (call signaling 1 minute; transfers and requests for the AI to draft 10 minutes) |
| NIP-98 | Signing for the HTTP endpoints (registration, notifications, recovery backup, reports, admin actions) |
| NIP-05, NIP-11 | The official account identifier (hello@tegami.chat), and relay information and running version |
| Blossom (kind 24242 signatures) | Storage for photos and files (`/upload` and `/<sha256>`). Stored and fetched by the sha256 of the encrypted data. `/stamp` for stickers is a Tegami extension |

Where no NIP applies, we use custom kinds that appear only inside encrypted envelopes. They are listed below in "Tegami's own kinds".

- <Badge text="Under discussion" variant="caution" /> If the proposals for key rotation and for protecting keys with a passkey (NIP pull requests #2137 and #2519) are adopted, we will consider following them.

## What the relay accepts

- The events accepted over WebSocket are kind 1059 envelopes with a single recipient (`p` tag). The size limit is 128KB
- Both reading and writing are allowed only for keys logged in with NIP-42. A login signature is valid if it is within 10 minutes, and one connection can have up to 20 subscriptions
- Only registered keys that have not been suspended can write. You can read only envelopes addressed to you, up to 500 per fetch, and they are deleted after 30 days. One person's inbox holds up to 10,000 envelopes, and up to 200 from people who registered without an invite ticket
- The sending limits (token bucket) are a burst of 300 envelopes per IP address (then 5 per second) and a burst of 120 per key (then 3 per second). One IP address can have up to 50 connections

## HTTP endpoints

Operations on photos, files and stickers need a kind 24242 signature. Every other write needs a NIP-98 signature. Only `/crash` needs no signature.

| Endpoint | Role | Status |
| --- | --- | --- |
| `POST /register` | Register a key (invite ticket or Turnstile) | <Badge text="Available" variant="success" /> |
| `PUT /upload`, `GET` and `HEAD /<sha256>` | Store and fetch photos and files. Up to 10MB | <Badge text="Available" variant="success" /> |
| `PUT /stamp`, `GET` and `HEAD` and `DELETE /stamp/<sha256>` | Stickers. 512KB each, up to 200 per person | <Badge text="Available" variant="success" /> |
| `PUT`, `GET`, `DELETE /backup/<id>` | Recovery code backup. Up to 64KB | <Badge text="Available" variant="success" /> |
| `POST`, `DELETE /push`, `GET /push/key` | Register a notification address, and the notification public key | <Badge text="Available" variant="success" /> |
| `POST /report` | Reports | <Badge text="Available" variant="success" /> |
| `GET /stats` | Weekly usage statistics (public) | <Badge text="Available" variant="success" /> |
| `POST /crash` | Error reports, only when the user allows it (not stored) | <Badge text="Available" variant="success" /> |
| `POST /admin` | Admin actions such as suspending a key, usable only with the operator's key | <Badge text="Available" variant="success" /> |
| `POST /register` (AI registration) | Register an AI's key. When the body carries the owner's signature (kind 25070), the relay remembers the key as an AI and counts its daily limit | <Badge text="Available" variant="success" /> |
| `POST /turn` | Issue short-lived credentials for the call relay (TURN). Only registered keys can use it. The request content is not stored | <Badge text="Available" variant="success" /> |
| `DELETE /account` | Delete an account. The relay deletes that key's envelopes, stickers, notification addresses, and registration | <Badge text="Available" variant="success" /> |
