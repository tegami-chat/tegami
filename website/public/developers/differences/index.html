How Tegami differs from common setups

This page is for developers who want to check how Tegami differs from a common setup, scene by scene, in seven scenes. In each table, the left column is the common setup and the right column is Tegami. Each technical term is explained in one sentence where it first appears. The other terms are in the glossary of the technical spec.

Measurement and ads

Section titled “Measurement and ads”

Tegami’s web version includes no trackers and no ad SDKs. CSP (Content Security Policy, which makes the browser limit where a page may load from) limits the scripts it can load to its own origin and to Cloudflare Turnstile, used for the human check at sign-up. There are no ad or analytics scripts.

Common setup Tegami
Remote config inserts ad slots into the chat list The chat list shows only conversations stored on the device
Tabs line up links to news and commerce There are only two tabs, “Chats” and “Friends”. There is no mechanism to insert ads or extra screens by remote config
Mistaken taps are also measured as clicks Taps and screen views are not sent as measurement events

The CSP is script-src 'self' https://challenges.cloudflare.com. connect-src is only its own origin and the relay. Cloudflare Web Analytics (RUM) is turned off. The other traffic that leaves is file storage through the relay (R2), STUN for calls (stun.cloudflare.com), and Web Push services. R2 is Cloudflare’s object storage, STUN is how a device finds its address as seen from outside, and Web Push is how notifications arrive even when the browser or app is closed.

Accounts and keys

Section titled “Accounts and keys”

A Tegami account is a Nostr key pair (secp256k1) made on the device, not a phone number. The secret key is encrypted with an AES-GCM key made from the output of the WebAuthn (the web standard that uses the browser’s or OS’s authentication without a password) PRF extension, and stored on the device.

Common setup Tegami
An SMS code confirms the phone number The device generates a key pair
The number is registered in the server’s user table The secret key is encrypted with an AES-GCM key made from the PRF output, and stored on the device
That number is tied to the account The public key is registered with the relay by a request signed with NIP-98

Registration uses an invite code or Cloudflare Turnstile. Turnstile is Cloudflare’s human check, which looks at the browser’s environment to tell bots apart. Records of who invited whom are deleted after 90 days. Signatures are Schnorr signatures (digital signatures over secp256k1). Key derivation uses HKDF (a way to make a fixed-length encryption key from a secret value), and encryption uses AES-GCM (an encryption method that encrypts and detects tampering at the same time). For authenticators that do not support the PRF extension, a non-extractable AES key is stored in IndexedDB.

Encryption

Section titled “Encryption”

A common app’s server records the sender, recipient and time in its database. Tegami encrypts a rumor (kind 14 or 15) with NIP-44 and puts it in an inner layer signed by the sender (seal, kind 13). It then encrypts and signs again with a throwaway key using NIP-44, and wraps the result in an envelope. For one-to-one chats it sends two: one for the recipient and one as a copy for yourself.

Common setup Tegami
Messages reach the API server over TLS (or E2EE, depending on the app) The device encrypts the message with NIP-44 and wraps it twice, in an inner layer and an envelope
The server keeps the sender, recipient and time in its database The relay returns only kind 1059 events whose p tag matches a key authenticated with NIP-42
That event log is used for ad delivery The relay deletes envelopes after 30 days, and the history stays on the user’s device

created_at on the inner layer and on the envelope is shifted back by up to 2 days (the nostr-tools implementation of NIP-59). TLS is the standard that encrypts the network path, and E2EE is a method where the sending device encrypts and only the receiving device decrypts.

Limits

Because writing also needs NIP-42 authentication and prior registration, the relay can link the sender’s public key, the recipient’s public key, the arrival time and the IP address. NIP-44 keeps using the same keys, so there is no forward secrecy.

Storage

Section titled “Storage”

Even if Tegami’s relay database were taken out whole, the chat contents would still be ciphertext. The messages stored in the relay’s database are envelope ciphertext. Photos and files are also encrypted with AES-GCM using their own keys before they are uploaded to storage.

Common setup Tegami
The database holds personal information in one place The messages in the database are kind 1059 ciphertext
The database is taken out The database is taken out (same as the common setup)
Phone numbers and profiles are read in plain text Even if taken out, it cannot be decrypted without the recipient’s secret key

What could be taken out is the following. The recipient’s public key (p tag), the arrival time, registered public keys and invite relationships (kept 90 days), Web Push endpoints (the URLs a browser’s push service issues as notification addresses) and keys, encrypted recovery backups, encrypted files and stickers in R2 (including size, SHA-256 and holder information), and report records. Report records hold the public keys of the reporter and the other person and the reason, and when attached, the plain text of recent messages is kept for 90 days.

What cannot be read even if taken out: regular messages, photos, files, stickers, and the plain text of backups.

Login

Section titled “Login”

Tegami has no login password at all. The secret key (nsec) is generated on the device, encrypted with a key made from the output of the WebAuthn PRF extension, and kept in per-origin storage. A passkey (a credential tied to an origin, used with biometrics or device unlock) is tied to the origin, so a fake domain cannot get the PRF output and cannot decrypt it.

Common setup Tegami
You log in with a password and an SMS one-time code The nsec stored on the device is decrypted with a passkey
An adversary-in-the-middle phishing attack (a fake site placed between you and the real login site, relaying what you type) steals both A fake domain cannot get the PRF output and cannot decrypt it
The attacker gets the session The nsec is never sent to the server

Limits

The decrypted secret key is used for signing in the browser’s memory, so it is weak against XSS (an attack that makes a web page run malicious JavaScript) and against tampering with the JavaScript we serve. For authenticators that do not support the PRF extension, a non-extractable AES key is stored in IndexedDB. A recovery code could be stolen by a trick that makes you type it into a fake site.

Usage records

Section titled “Usage records”

Tegami’s app has no analytics SDK. The relay keeps daily overall counts for 183 days and aggregates them for the operator, and publishes only the totals of finished weeks, for the latest 24 weeks. They are published at https://relay.tegami.chat/stats and https://tegami.chat/status.

Common setup Tegami
An analytics SDK sends taps and screen views as events The client sends no interaction events
Events are stored per user ID The relay counts only daily overall totals internally, and estimates the number of active keys with a secret value that changes daily and HyperLogLog
Interest segments are built from those records What is published is only the totals of finished weeks (0 to 9 shown as 0, 10 and above rounded up to a multiple of 10) and the daily average number of keys

Workers invocation logs (a record of each request’s execution) are turned off. Output such as crash reports the user allowed (console.log) stays in Workers Logs for a few days. Daily totals are deleted after 183 days and only the operator can view them. The public page shows finished weeks (weeks start on Monday in UTC), only for the latest 24 weeks.

AI

Section titled “AI”

In Tegami, an AI is someone who holds its own key. tegami-agent holds its own Nostr key on your computer and talks over the same NIP-17 as people. Your AI subscription and API key are never handed to Tegami’s servers. What you let the AI read is sent to the AI provider through your local claude -p (the command that runs Claude Code by passing a prompt directly and returning the result on standard output) or similar. tegami-agent also runs as an MCP server (a mechanism that lets an AI call outside data and features in a common format).

Common setup Tegami
You use an AI feature built into the app tegami-agent runs on your computer and calls your local Claude Code or similar
The chat history, including the other person’s words, goes to the provider’s API Before calling an AI into a chat, we ask everyone for consent (coming soon)
The other person’s consent is not asked AI permissions are controlled in four levels (use of AI, AI model, AI friend, friend), and every decision is recorded on the device

Conversations with the AI are NIP-17 envelopes too. The mechanism that asks everyone in a chat for consent, and the mechanism that lets the other person choose “Don’t let their AI read my messages”, are implemented but not yet in production (disabled by default). Cryptography cannot prevent the recipient from passing the words they decrypted on their own device to an AI.
