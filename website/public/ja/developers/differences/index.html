よくある構成との違い

よくある構成を左に、Tegamiを右に並べた7つの場面です。場面の下に、使っている専門用語の説明があります。

トラッカーも広告SDKも入っていない。

Section titled “トラッカーも広告SDKも入っていない。”

Web版はCSPにより、読み込めるスクリプトを自身のオリジンと、新規登録時の人間確認に使うCloudflare Turnstileだけに限っています。広告や解析のスクリプトはありません。

よくある構成

  1. リモート設定でトーク一覧に広告枠が差し込まれる
  2. タブにニュースやコマースへの導線が並ぶ
  3. 誤タップもクリックとして計測される

Tegami

  1. トーク一覧には端末に保存した会話だけを表示する
  2. 切り替えは「トーク」と「友だち」の2つだけ。広告や余分な画面をリモート設定で差し込む仕組みはない
  3. タップや画面表示を計測イベントとして送信しない

ノート

CSP：script-src ‘self’ https://challenges.cloudflare.com。connect-srcは自身のオリジンとリレーだけです。Cloudflare Web Analytics（RUM）は無効です。そのほか外部へ出る通信は、リレー経由のファイルストレージ（R2）、通話用のSTUN（stun.cloudflare.com）、Web Pushサービスです。

用語の説明
  • トラッカー：Webサイトやアプリ上でユーザーの操作や閲覧行動を収集し、外部へ送信して追跡するスクリプトや仕組みです。
  • 広告SDK：アプリ内に広告枠を表示し、広告の表示回数やクリック数を計測するために組み込まれる外部ソフトウェア開発キットです。
  • CSP：Content Security Policyの略で、Webページが読み込みや実行や通信を許可する送信元をHTTPヘッダなどで制限するブラウザのセキュリティ仕組みです。
  • オリジン：URLのスキーム（httpsなど）、ホスト名、ポート番号の組み合わせで決まるWeb上のセキュリティ境界の単位です。
  • Cloudflare Turnstile：ブラウザの環境検証などによって自動ボットアクセスを判別するCloudflareの人間確認ツールです。
  • リモート設定：アプリ本体を更新せずに、サーバーから設定値を配信して画面構成や広告枠や機能を動的に切り替える仕組みです。
  • 計測イベント：アプリ内でユーザーがどの画面を見たかやどこをタップしたかといった操作情報を分析サーバーへ送信するテレメトリデータです。
  • script-src ‘self’：CSPのscript-srcディレクティブで、Webアプリ自身のオリジン（‘self’）から配信されたJavaScriptの実行だけを許可する指定です。
  • connect-src：CSPにおいて、ページ内のスクリプトがfetchやWebSocketなどで接続できる通信先URLを制限するディレクティブです。
  • Cloudflare Web Analytics（RUM）：ブラウザ上で計測用JavaScriptを実行してページ表示やアクセス状況を収集するCloudflareの実ユーザー計測機能です。
  • R2：Cloudflareが提供するS3互換のオブジェクトストレージサービスです。
  • STUN：NAT越え通信のために端末自身のグローバルIPアドレスとポート番号を調べる標準プロトコル（Session Traversal Utilities for NAT）です。
  • Web Push：Webアプリが閉じられていてもブラウザやOSの配信基盤経由で通知を受信できるWeb標準仕様です。

電話番号ではなくsecp256k1の鍵。

Section titled “電話番号ではなくsecp256k1の鍵。”

アカウントは端末で生成するNostrの鍵ペアです。秘密鍵はWebAuthnのPRF拡張の出力から作ったAES-GCM鍵で暗号化し、端末内に保存します。

よくある構成

  1. SMSの認証コードで電話番号を確かめる
  2. 番号がサーバーのユーザーテーブルに登録される
  3. その番号がアカウントに紐づけられる

Tegami

  1. 端末で鍵ペアを生成する
  2. 秘密鍵はPRFの出力から作ったAES-GCM鍵で暗号化し、端末内に保存する
  3. NIP-98で署名したリクエストで公開鍵をリレーに登録する

ノート

使用仕様：Nostrの鍵（secp256k1、Schnorr署名）、WebAuthnのPRF拡張、HKDF、AES-GCM、NIP-98。登録には招待コードかCloudflare Turnstileを使い、誰が誰を招待したかの記録は90日で消去します。PRF拡張に非対応の認証器では、エクスポートできないAES鍵をIndexedDBに保存します。

用語の説明
  • secp256k1：ビットコインやNostrで標準的に採用されている楕円曲線暗号のパラメータ仕様です。
  • Nostr：公開鍵暗号と電子署名を用い、リレーサーバー経由で中央のユーザーDBに縛られずイベントをやり取りするオープンプロトコルです。
  • 鍵ペア：数学的に対になる公開鍵と秘密鍵の2つ1組のデータです。
  • 秘密鍵：所有者だけが保持し、データへの署名や自分宛て暗号文の復号に使う鍵データです。
  • WebAuthn：生体認証やセキュリティキーを使い、パスワードなしでブラウザやOS上の認証と鍵操作を行うWeb標準APIです。
  • PRF拡張：WebAuthnの拡張機能（Pseudo-Random Function）の1つで、パスキー認証時にオリジンと資格情報に紐づく決定的な秘密の出力値を取り出せる仕組みです。
  • AES-GCM：AES暗号にGalois/Counter Modeを組み合わせた、データの機密性と改ざん検知を同時に提供する認証付き暗号方式です。
  • npub：Nostrの公開鍵をBech32形式（先頭がnpub1で始まる文字列）にエンコードした可読表現です。
  • NIP-98：Nostrの秘密鍵でHTTPリクエストのURLやメソッドなどに署名し、HTTP通信の認証を行う仕様です。
  • Schnorr署名：secp256k1曲線上でNostrが採用しているデジタル署名方式で、秘密鍵の所有者本人がイベントを作成したことを証明します。
  • HKDF：HMAC-based Key Derivation Functionの略で、秘密の入力値から暗号用途に適した安全で固定長の暗号鍵を生成する鍵導出関数です。
  • 認証器：WebAuthnにおいて資格情報を保持し、生体認証やPINの検証後に署名やPRF値を返すハードウェアまたはOSやブラウザ上の仕組みです。
  • エクスポートできないAES鍵：Web Crypto APIにおいて、JavaScriptから鍵の生のバイト列を取り出せない設定（extractableがfalse）で生成したAES暗号鍵です。
  • IndexedDB：Webブラウザがオリジンごとに提供する、構造化データや暗号鍵オブジェクトなどを永続保存できるローカルデータベースAPIです。

NIP-17で封をしてから送る。

Section titled “NIP-17で封をしてから送る。”

一般的なアプリのサーバーは送信者、受信者、時刻をデータベースに記録します。Tegamiはrumor（kind 14または15）をNIP-44で暗号化し、送信者が署名した内側の層（kind 13）に収めます。さらに使い捨ての鍵で再びNIP-44による暗号化と署名をして、封筒（NIP-59 の gift wrap。暗号化したメッセージを入れた入れ物。kind 1059）で包みます。1対1では宛先用と自分用の控えの2通を送ります。

よくある構成

  1. メッセージはTLS（アプリによってはE2EE）でAPIサーバーに届く
  2. サーバーが送信者、受信者、時刻をデータベースに残す
  3. そのイベントログが広告配信に使われる

Tegami

  1. 端末内でメッセージをNIP-44で暗号化し、内側の層と封筒で2重に包む
  2. リレーはNIP-42で認証済みの鍵に対し、pタグが一致するkind 1059だけを返す
  3. リレーは30日後に封筒を削除し、履歴は利用者の端末に残る

ノート

使用仕様：NIP-17、NIP-44、NIP-59、NIP-42。内側の層と封筒のcreated_atは最大2日前にずらします（nostr-toolsのNIP-59実装）。限界：書き込みにもNIP-42認証と事前登録が必要なため、リレーは送信元の公開鍵、宛先の公開鍵、到着時刻、IPアドレスを結びつけられます。NIP-44は同じ鍵を使い続けるため、前方秘匿性はありません。

用語の説明
  • APIサーバー：クライアントからのリクエストを処理し、データ保存やメッセージ中継を一括して担う中央サーバーです。
  • リレー：Nostrプロトコルにおいて、クライアントが送ったイベントを受信して保持し、条件に合うクライアントへ配信するサーバーです。
  • NIP-17：Nostrにおける非公開ダイレクトメッセージの仕様です（NIPはNostrの仕様提案番号）。
  • rumor：Nostrの暗号化メッセージにおいて、送信者の署名を付けない状態の生のイベントデータ（テキストのkind 14やファイルのkind 15）です。
  • kind：Nostrのイベントデータに含まれ、イベントの種別を識別するための整数値です。
  • NIP-44：送信者と受信者の鍵から共有鍵を作ってデータを暗号化する、Nostrの認証付き暗号仕様です。
  • seal：rumorをNIP-44で暗号化し、送信者の秘密鍵で署名した内側のイベント（kind 13）です。
  • 使い捨ての鍵：暗号化と署名のたびに新しく生成し、1度使った後に破棄する一時的なNostr鍵ペアです。
  • gift wrap：sealを使い捨ての鍵でNIP-44暗号化し、その使い捨ての鍵で署名した外側のイベント（kind 1059）です。
  • TLS：インターネット上でクライアントとサーバー間の通信経路を暗号化する標準プロトコル（Transport Layer Security）です。
  • E2EE：エンドツーエンド暗号化（End-to-End Encryption）の略で、送信者の端末で暗号化し受信者の端末だけで復号することで中継サーバーに平文を見せない仕組みです。
  • イベントログ：ユーザーの操作やメッセージ送受信などの発生履歴を時系列で記録したログデータです。
  • NIP-42：Nostrでクライアントがリレーに対し署名付きチャレンジ応答で自分の公開鍵を認証するための仕様です。
  • pタグ：Nostrイベントのタグ配列において、宛先や言及対象となる公開鍵（16進文字列）を指定するタグです。
  • NIP-59：Nostrイベントをrumor、seal、gift wrapの段階構造で包み、送信者や作成時刻などのメタデータを隠す仕様です。
  • created_at：Nostrイベントの作成日時を表すUNIXタイムスタンプのフィールドです。
  • nostr-tools：JavaScriptとTypeScript向けにNostrの鍵操作、署名、暗号化、リレー通信などを提供するオープンソースライブラリです。
  • 公開鍵：公開鍵暗号において他者へ共有できる鍵データで、暗号化、署名検証、アカウント識別に使います。
  • IPアドレス：ネットワーク上で通信元の機器を識別するためのアドレスです。
  • 前方秘匿性：長期的な秘密鍵が将来漏洩しても、過去に送受信して暗号化した通信内容までは復号できないという暗号プロトコルの性質です。

ダンプされても、チャットは暗号文のまま。

Section titled “ダンプされても、チャットは暗号文のまま。”

リレーのデータベースに保存されるメッセージは封筒の暗号文です。写真やファイルも個別の鍵を使い、AES-GCMで暗号化してからストレージにアップロードします。

よくある構成

  1. データベースに個人情報がまとまって入っている
  2. データベースが外に持ち出される
  3. 電話番号やプロフィールが平文のまま読まれる

Tegami

  1. データベースのメッセージはkind 1059の暗号文
  2. データベースが外に持ち出される
  3. 持ち出されても、受信者の秘密鍵がなければ復号できない

ノート

持ち出される可能性があるもの：宛先の公開鍵（pタグ）、到着時刻、登録済みの公開鍵と招待関係（90日保持）、Web Pushのエンドポイントと鍵、暗号化した復旧用バックアップ、R2の暗号化ファイルとスタンプ（サイズ、SHA-256、保持者情報を含む）、通報記録（通報者と相手の公開鍵、理由、添付された場合は直近メッセージの平文を90日保持）。持ち出されても読めないもの：通常のメッセージ、写真、ファイル、スタンプ、バックアップの平文。

用語の説明
  • ダンプ：データベースに保存されているデータをファイルなどに丸ごと書き出すこと、またその書き出されたデータです。
  • 暗号文：暗号化アルゴリズムで変換され、正しい復号鍵がなければ元のデータを読めない状態のデータです。
  • 平文：暗号化されていない、そのまま内容を読み取れる状態の生データです。
  • エンドポイント：Web Push通知の配信先を特定するためにブラウザのプッシュサービスから発行される専用URLです。
  • SHA-256：任意の入力データから256ビットの固定長ハッシュ値を算出する暗号学的ハッシュ関数です。

ログインのパスワードがそもそもない。

Section titled “ログインのパスワードがそもそもない。”

秘密鍵（nsec）は端末で生成し、WebAuthnのPRF拡張の出力から作った鍵で暗号化してオリジンごとの保存領域に置きます。パスキーはオリジンに紐づくため、偽のドメインではPRFの出力が得られず復号できません。

よくある構成

  1. パスワードとSMSのワンタイムコードでログインする
  2. 中継型フィッシングで両方を横取りされる
  3. 攻撃者がセッションを手に入れる

Tegami

  1. 端末に保存したnsecをパスキーで復号する
  2. 偽のドメインではPRFの出力が得られず、復号できない
  3. nsecはサーバーに送信しない

ノート

使用仕様：WebAuthnのPRF拡張、HKDF、AES-GCM。限界：復号した秘密鍵はブラウザのメモリ上で署名に使うため、XSSや配信JavaScriptの改ざんには弱いです。PRF拡張に非対応の認証器では、エクスポートできないAES鍵をIndexedDBに保存します。復旧コードは偽サイトに入力させる手口で盗まれるおそれがあります。

用語の説明
  • nsec：Nostrの秘密鍵をBech32形式（先頭がnsec1で始まる文字列）にエンコードした表現です。
  • パスキー：FIDO2とWebAuthnに基づき、生体認証や端末のロック解除を用いて認証を行うオリジン紐付きの資格情報です。
  • ワンタイムコード：1回のログインや認証にだけ有効な使い捨ての確認コードで、SMSなどで送られる方式が一般的です。
  • 中継型フィッシング：攻撃者が本物のログインサイトと利用者の間に偽サイトを挟み、入力されたパスワードやワンタイムコードをリアルタイムで中継して認証後のセッションを奪う攻撃です。
  • セッション奪取：ログインした後に発行されるセッションのトークンやクッキーを攻撃者が横取りし、本人になりすまして操作することです。
  • XSS：Cross-Site Scriptingの略で、Webサイトの脆弱性を突いて悪意のあるJavaScriptをブラウザ上で実行させる攻撃です。
  • 復旧コード：端末をすべてなくした時にアカウントを戻すための28文字のコード（140ビット）です。

イベントを計測していない。

Section titled “イベントを計測していない。”

アプリに解析SDKはありません。リレーは日ごとの全体件数を183日保持して運営者向けに集計し、終わった週の合計だけを直近24週分、外部公開しています（https://relay.tegami.chat/stats、https://tegami.chat/status）。

よくある構成

  1. 解析SDKがタップや画面表示をイベントとして送る
  2. イベントがユーザーIDごとに保存される
  3. その記録から興味のセグメントが作られる

Tegami

  1. クライアントは操作イベントを送らない
  2. リレーは日ごとの全体件数だけを内部で数え、アクティブ鍵数の概算には日替わりの秘密の値とHyperLogLogを使う
  3. 公開するのは終わった週の合計（0から9は0、10以上は10の倍数に切り上げ）と1日平均の鍵数のみ

ノート

Workersのinvocation logsは無効です。利用者が許可したクラッシュ報告などの出力（console.log）はWorkers Logsに数日残ります。日ごとの集計は183日で削除し、運営者のみ閲覧できます。公開ページ（https://relay.tegami.chat/stats、https://tegami.chat/status）には、終わった週（UTCの月曜始まり）を直近24週分だけ出します。

用語の説明
  • 解析SDK：アプリに組み込んで画面表示やタップや滞在時間などの操作ログを自動収集し分析サーバーへ送る外部開発キットです。
  • イベント：アプリ解析の文脈で、ユーザーのタップや画面表示など1回ごとの操作を記録し送信するデータ単位です（Nostrプロトコル上のイベントとは別概念）。
  • セグメント：収集した行動イベントや属性をもとに、興味や行動傾向が似ているユーザー群を分類したグループです。
  • クライアント：サーバーやリレーに接続して動作するユーザー側のアプリやWebブラウザ上のソフトウェアです。
  • 日替わりの秘密の値：1日ごとに新しく生成して使い、その日が終わると破棄される一時的な秘密の値です。
  • HyperLogLog：データ要素そのものを記憶せずにハッシュ値のビットパターンから重複を除いた要素数だけを極めて少ないメモリで概算する確率的アルゴリズムです。
  • Workers：Cloudflareのエッジネットワーク上でJavaScriptなどを実行するサーバーレス実行基盤（Cloudflare Workers）です。
  • invocation logs：Cloudflare WorkersにおいてHTTPリクエストや関数呼び出しごとの実行履歴とメタデータを自動記録するログ機能です。
  • console.log：JavaScriptで実行中のログメッセージやエラー情報を出力する標準関数です。
  • Workers Logs：Cloudflare Workersの実行中に出力されたログを一時的に保持し閲覧できるログ収集基盤です。
  • UTC：協定世界時（Coordinated Universal Time）の略で、タイムゾーンに依存しない世界標準の基準時刻です。

AIは自分の鍵を持つ相手。

Section titled “AIは自分の鍵を持つ相手。”

tegami-agentはPC上で独自のNostr鍵を持ち、人間と同じNIP-17でやり取りします。AIの契約やAPIキーをTegamiのサーバーに渡すことはありません。AIに読ませた内容は手元のclaude -pなどを通じてAI提供元に送られます。またtegami-agentはMCPサーバーとしても動作します。

よくある構成

  1. アプリに組み込まれたAI機能を使う
  2. 相手の発言を含むトーク履歴が提供元のAPIに送られる
  3. 相手の同意は求められない

Tegami

  1. tegami-agentがPC上で動き、手元のClaude Codeなどを呼ぶ
  2. トークにAIを呼ぶ前に、全員の同意を求める（公開待ち）
  3. AIの権限は4段（AIの使用、AIモデル、AI友だち、友だち）で制御し、判断はすべて端末に記録する

ノート

AIとの会話もNIP-17の封筒です。トークの全員の同意を求める仕組みと、相手が「自分の文を相手のAIに読ませない」を選べる仕組みは実装済みですが、本番にはまだ出していません（初期設定は無効）。受信者が自分の端末で復号した発言をAIに渡す行為までは、暗号の仕組みでは防げません。

用語の説明
  • tegami-agent：利用者のPC上で動作するTegamiのAI連携用エージェントプログラムで、独自のNostr鍵を持ち人間と同じNIP-17のgift wrapでやり取りします。
  • APIキー：外部のAPIサービスを利用する際の契約者認証や課金紐づけに使う秘密のトークン文字列です。
  • claude -p：Anthropic社のコマンドラインAIツールであるClaude Codeを、非対話モード（プロンプトを直接渡して結果を標準出力に返すオプション-p）で実行するコマンドです。
  • MCPサーバー：Model Context Protocol（MCP）に準拠し、AIクライアントから外部データや機能を共通の形式で呼び出せるようにするサーバープログラムです。
  • Claude Code：Anthropic社が提供している、ローカル端末上で動作するAI開発や作業を支援するCLIツールです。
  • API：Application Programming Interfaceの略で、ソフトウェア同士がネットワーク越しなどに機能やデータをやり取りするための接続窓口と規約です。
